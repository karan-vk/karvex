**工作流**是一份被保存、带版本的计划:命名的节点、它们之间的依赖关系,以及每个节点的模型需求。**运行(run)**把这份计划交给一个交互式的 **Claude Code 团队负责人**,让它在一个 Herdr 面板里工作,然后袖手旁观。负责人读取计划、创建 Claude Code 的共享任务列表、把队友作为各自独立的 Herdr 面板启动,并自行决定重试、重新分配和完成判定。Herdr 不再执行计划——它只负责定义计划、启动负责人、观察团队自己的任务列表并把它转成运行记录,以及保存发生过的一切。

工作流适合那些你想定义一次、反复运行的多步骤、多智能体工作,比如计划 → 实现 → 评审。对于你已经在运行的智能体之间一次性的并行协调,请改用[智能体自动化](/docs/agent-automation/)。而且,由于一次运行就是一个真正的 Claude Code 智能体团队,请在阅读本页的同时也阅读[Claude Agent Teams](/docs/integrations/#claude-agent-teams)——那里写到的团队能做什么、不能做什么,对 Herdr 启动的运行同样成立。

## 什么是工作流

**工作流**是一个具名容器,装着一个或多个 **kvdag 版本**——不可变的图定义。`kvx workflow create` 创建第一个版本;`kvx workflow update` 在它之上创作新版本。编辑从不原地修改某个版本,而总是产生一个新版本,因此过去的运行始终可以对照它实际运行过的那个版本被重现。

启动一次运行会依次做五件事:解析定义版本及其参数,把它们渲染成一份**负责人提示词**——一份告诉负责人该创建哪些任务、按什么顺序、带着怎样的 `blockedBy` 依赖关系的 Markdown 计划——在一个新面板里启动一个执行该计划的交互式 `claude`,识别负责人创建的 Claude Code 团队,然后开始观察。以前属于 Herdr 的工作——调度、认领、重试、把结果对照 schema 判定——现在都是负责人的工作,通过 Claude Code 自己的共享任务列表和负责人自己的判断完成。运行只有在负责人调用 `kvx workflow run finish` 明确宣告结束时才会结束。

## 定义格式

`kvx workflow create` 和 `kvx workflow update` 读取一份 TOML 或 JSON 格式的定义文档——文件扩展名决定格式。格式本身没有变化;变的是一次运行拿它做什么。下面是一个完整示例,只包含现在真正起作用的部分:

```toml
name = "ship-feature"
description = "plan → implement → review"
contract = """
Read the codebase before proposing changes. Keep commits small and reviewable.
"""

# Declared run-argument namespace. Without this, `{{goal}}` below has no inbound
# edge port to resolve against and workflow.create rejects the document.
[[arg]]
name = "goal"
required = true
description = "what to build"

[[node]]
key = "plan"
label = "Plan"
demand = "critical"
prompt_template = "Produce an implementation plan for: {{goal}}"

[[node]]
key = "implement"
label = "Implement"
demand = "peak"
prompt_template = "Implement this plan:\n{{plan}}"

[[edge]]
from = "plan"
to = "implement"
```

`contract` 会被添加到负责人被要求向每个它所启动的队友重复的通用指示的开头——把跨节点的共同规则写在这里,而不是在每个节点里重复。`default_tier`(`auto`、`max`、`high`、`medium` 或 `low`,默认 `high`)是当 `kvx workflow run start` 没有给出 `--tier` 时,该工作流的运行所使用的等级。等级现在只做一件事:按每个节点的 `demand`,收窄给负责人的模型/精力提示(`--tier low` 建议全程使用 sonnet、低精力;`--tier max` 建议使用可用的最强模型、最大精力)——这只是提示而非规则,如果某个任务确实值得,负责人可以自由投入更多。等级过去还会收窄的增长上限(`max_nodes`、`max_depth`)属于已被移除的引擎,参见下面的说明。

每个 `[[arg]]` 在运行参数命名空间里声明一个条目,在运行时用 `--arg name=value` 填充。每个 `[[node]]` 需要唯一的 `key`、`label` 和 `prompt_template`;如果给出了 `role`,负责人会多得到一行关于该节点的说明。`demand`(`peak`、`critical`、`standard` 或 `light`,默认 `standard`)是对负责人应该为该节点使用哪种模型和精力的提示——不会被强制执行,如果某个任务确实值得,负责人可以自由投入更多。每条 `[[edge]]` 只需要 `from` 和 `to`:它会变成负责人被要求创建的任务计划里的一条 `blockedBy` 关系,仅此而已。

`prompt_template` 中的 `{{name}}` 占位符必须能解析为一个已声明的参数,或者一条入边的 `port` 名——`workflow.create` 仍然会拒绝含有未解析占位符的文档,有环或不可达的图在创作时仍然会被拒绝。从已声明参数填充的占位符,会在负责人看到之前就被替换。指向某条边 `port` 的占位符**不再**被替换——因为 Herdr 不执行节点,也就没有上游检查点可以拿来填充。它会原样留在渲染出的计划里,负责人会被告知哪些任务描述里还留着 `{{slot}}` 标记,并被要求在启动那个队友时,自己用阻塞任务的实际结果去填上它。

被拒绝的定义什么也不会写入。`name` 在所有工作流之间是唯一的——如果撞上了,参见 `workflow_name_taken` 和 `kvx workflow update`。带上声明过的参数运行它:

```bash
kvx workflow run start ship-feature --arg goal="add dark mode"
```

:::note[为兼容性保留的字段]
节点上的 `kind`、`runner`、`command`、`output_schema`、`max_attempts`、`timeout_ms`、`isolation`、`is_template`、`expand_allow`、`expand_max`,以及边上的 `kind`、`condition`、`payload`、`port`,现在仍然都能被解析——这次改造之前写的定义仍然能加载。文档级别的 `max_depth`/`max_nodes` 也仍然能被解析,而且经过等级收窄后的运行**实际生效**的上限仍然会被计算并记录在运行行上。但这些都不会改变负责人被告知的内容,也不会改变运行的行为——它们是这次发布中被移除的自定义执行引擎的词汇(经 schema 校验的节点完成、受增长上限约束的节点扩展、作为普通进程运行的 `runner = "command"` 节点、被强制执行的节点/运行预算),在新模型里都没有替代品——负责人可以按自己判断创建任意多的任务。从现在起你自己撰写的文档里应该去掉这些字段;一个工作流的整个计划现在只寄居在 `key`、`label`、`role`、`prompt_template`、`demand`,以及节点之间的边里。这份清单里唯一还在起作用的字段是 `demand`:它和运行的等级一起,决定了负责人为该节点得到的模型/精力提示。
:::

## 要求与限制

一次运行是一个真正的、实验性的 Claude Code 功能在 Herdr 内部运行,而不是 Herdr 独有的机制,所以它的限制大多来自 Claude Code 自身。`kvx workflow run start` 会尽力做预检查,并以清晰的信息拒绝,而不是悄悄启动一个根本无法工作的负责人:

- **智能体团队是实验性功能,并按版本开关控制。** 需要 Claude Code 2.1.224 或更高版本;更老的版本会作为普通的、没有智能体团队功能的 `claude` 运行。Herdr 在启动负责人之前会检查 `claude --version`,低于这个版本就会拒绝(`workflow_lead_unavailable`)。Herdr 还会在负责人自己的面板里设置 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`,所以对于 Herdr 启动的运行,你不需要自己设置这个开关。
- **分屏队友需要 Herdr 的 tmux 垫片。** 每次运行都以 `--teammate-mode tmux` 启动,这正是让每个队友成为真正的 Herdr 面板、而不是与负责人终端共享的不可见的进程内会话的原因——这也是队友无法在 `/resume` 中存活的原因。垫片如何工作、什么会遮住它,参见[Claude Agent Teams](/docs/integrations/#claude-agent-teams)。
- **任务状态可能滞后。** 上游文档对此说得很明白:队友有时不会把已经完成的任务标记为完成。因此 Herdr 的 DAG 视图并排展示两个信号——任务自身的状态,以及所有者面板的实时智能体状态——正是为了让你能在记录追上现实之前发现一个实际已经完成的任务。如果某次运行看起来卡住了,先看面板,再相信任务列表。
- **一个会话只有一个团队,不允许嵌套团队。** 一个负责人会话恰好拥有一个团队;队友不能启动自己的队友。出于同样的原因,Herdr 每台服务器只运行一个负责人——在另一个运行仍然存活时启动新运行会被拒绝(`workflow_run_in_flight`),而不是得到第二个、无法管理的团队。
- **不受信任的目录会悄悄吞掉负责人的计划。** Claude Code 的文件夹信任对话框不仅会阻止一个不受信任的 `cwd`,还会把负责人的初始提示词完全丢弃,于是在那里启动的运行会看起来健康地起来,却无事可做。Herdr 会预检 `~/.claude.json` 里的信任记录,并给出确切的解决办法后拒绝(`workflow_lead_unavailable`):在该目录里手动运行一次 `claude` 并接受对话框。
- **跨会话消息需要 Claude Code 2.1.224 及以上版本,并且只支持 macOS 或 Linux。** Herdr 不会替你发消息——操作方式是点击面板并输入——但在该功能可用时,负责人和它的队友可以互相发消息,也可以给你的其他 Claude Code 会话发消息。在原生 Windows 上,无论 Claude Code 版本如何都不可用;而且只在 Claude Code 尚未缓存过功能开关的账号上才生效的环境变量,可能会悄悄禁用它。唯一值得信任的实时信号,是面板 `/status` 里的 `Peer address` 一行。
- **运行按设计是有人值守的。** 没有无人值守模式。权限确认和计划批准请求都会出现在触发它们的那个面板里——通常是负责人的面板,因为队友的权限请求默认会上报给负责人——运行就在那里干等,直到有人回答。这是刻意为之的:v1 的整个交互模型就是"点一下面板"。

## 启动一次运行

```bash
kvx workflow run start <name|id> [--tier auto|max|high|medium|low] [--arg KEY=VALUE]... [--json]
```

启动一次运行会在当前工作区里拆分出当前聚焦的面板,并以不带位置参数提示词的方式启动一个交互式 `claude`——把提示词通过 argv 传给一个全新的 `claude` 会被悄悄丢弃,这是 Herdr 在其他智能体面板上早已知道的同一种失败模式。取而代之,Herdr 会等待该面板的会话启动,然后通过和 `kvx agent prompt` 相同的机制,只发送一次指令:读取渲染出的计划文件并照着做。从那之后就是负责人自己的事了:它读取计划,按计划指定的确切主题和 `blockedBy` 结构创建任务(任务主题是 `<node-id>: <label>`,`node-id:` 这个前缀正是之后 Herdr 用来把任务对应回节点的依据),并以它们所负责的节点命名来启动队友。

一旦 Claude Code 的团队配置出现,Herdr 就会识别出该运行的团队——依据负责人面板的 `cwd` 和团队的创建时间来匹配,一旦绑定就不会再重新推导。此时运行的状态变为 `running`,`kvx workflow run show <run_id> --json` 会返回绑定好的 `lead_pane_id`、`lead_session_id` 和 `team_name`。面向人类的默认输出不会打印这些字段,所以当你需要的是负责人自己的面板 ID 而不是节点所有者的面板 ID 时,请使用 `--json`。

## 观察一次运行

每次运行都是被投影出来的,而不是被追踪的:一个很小的轮询器每两秒读取一次 Claude Code 自己的状态——任务用 `~/.claude/tasks/<team>/*.json`,团队名册用 `~/.claude/teams/<team>/config.json`——并把它转成运行记录。主题以某个定义节点的 `<node-id>:` 前缀开头的任务,会更新对应的节点;负责人创建的、匹配不到任何节点的任务不会被丢弃,而是记录为保留路径 `.task/<n>` 下的**涌现(emergent)**节点,因为负责人有权拆分、合并或增加计划没有要求的工作。被投影的节点状态只有恰好三种取值——`pending`、`running`(对应 Claude Code 的 `in_progress`)、`succeeded`(对应 `completed`)——映射了任务列表自身的三态词汇;老的、由引擎执行的运行可能带有的那些更丰富的状态(`failed`、`blocked`、`needs_attention`、`skipped`、`restored`)属于这次改造之前的运行,不会出现在新的运行上。团队成员信息是在每次观察到变化时被快照下来的,而不是实时读取的,因为 Claude Code 会在负责人的会话结束的那一刻删除团队配置目录。

### DAG 视图

用 `prefix+shift+F`,或从侧边栏启动器(**workflow dag**)打开一次运行的 DAG 视图。节点状态分两层展示:来自投影的任务自身状态,以及——通过任务的 `owner` 关联到 Herdr 常规的、按面板划分的智能体检测——该所有者的面板是 `working`、`idle` 还是 `needs input`。这就是对任务状态滞后问题的实际答案:当两者不一致时,相信面板而不是任务记录。

| 输入 | 动作 |
| --- | --- |
| `h` / `j` / `k` / `l` 或方向键 | 移动选择 |
| 点击某个节点 | 选中它 |
| `Enter`,或双击某个节点 | 聚焦到该节点的面板 |
| `Esc` | 离开 DAG 视图 |

这就是现在页脚的全部内容——`enter focus pane · hjkl move · esc`。没有 `s` steer,没有 `i` interrogate,也没有 `Shift+I` reconstruct:那些是针对 Herdr 自己执行的节点的操作,而现在的节点是真正的队友自己的面板。要操作它,打开那个面板就行——见下一节。

### 运行浏览器

`prefix+shift+B` 会打开这台服务器知道的所有运行,跨越所有工作流,按最新排在最前。`Enter` 会在 DAG 视图里打开某次运行——如果还在运行就是实时的,否则就是只读的历史记录。详情条会显示所选运行的参数,以及(如果已经有的话)其摘要的结果和第一条要点。

## 操作一次运行

节点的面板是一个完全独立的 Claude Code 会话——在分屏模式下,和 Claude Code 在其他地方启动的任何队友完全一样。不再有 Herdr 中介的 steer、interrupt、restart 了:

- **要重新引导某一个队友**,打开它的面板(在 DAG 视图里按 `Enter`,或用 `kvx workflow node show <run_id> <path>` 找到它的 `pane_id`)并直接输入。你是在直接和那个 Claude 会话对话。
- **要重新引导整次运行**——调整优先级、启动更多队友、放弃某个任务——打开负责人的面板(`kvx workflow run show <run_id> --json` 会以 `lead_pane_id` 的名义给出它)并告诉它你想要什么。只有负责人能重新分配工作,或者去催促一个卡住的队友;Herdr 自己都做不到这两件事。
- **负责人面板里的权限确认会阻塞整次运行。** 队友的权限请求默认会上报给负责人,所以一次看起来卡住的运行,很多时候只是在那一个面板里等待一个答案而已。

早期版本有 `kvx workflow node steer|interrupt|restart|complete|expand|interrogate`。CLI 目前仍然能解析这全部六个命令,但服务器会对每一个都以 `workflow_node_verb_retired` 作答,并指向面板——因为它们操作的是 Herdr 已经不再执行的节点。`kvx workflow node show <run_id> <path> [--json]` 仍然有效;它是对投影的一次读取,和 `run show` 一样。

## 结束一次运行

```bash
kvx workflow run finish [--run <run_id>] (--summary-file <path> | --summary <text>) [--outcome <word>] [--json]
```

计划会指示负责人,在所有任务完成、或者它已经断定这次运行无法再推进时,恰好做这一件事:把运行摘要写到一个文件里,然后带着它调用 `run finish`。`KARVEX_WORKFLOW_RUN_ID` 已经在负责人自己的面板里导出了,所以它只需要提供摘要。这一次调用就取代了整个旧的摘要生成子系统——不再有由引擎判定的结论了。如果这次运行确实失败了,负责人仍然会调用 `finish` 并如实说明:运行自身的状态无论如何都会变成 `succeeded`(自我报告能到达的终态只有这一个),而实际发生了什么、是否成功这个真相,存在于 `outcome` 这个词和摘要正文里,只需一次 `kvx workflow summary show` 就能看到。

```bash
kvx workflow run cancel <run_id> [--json]
```

取消会把运行标记为 `cancelled` 并关闭负责人的面板。不需要做任务级别的收尾:队友属于负责人,而不属于 Herdr,所以没有什么东西会一个个走过团队去关闭面板。

如果负责人的面板自己关闭了——手动关闭、崩溃,或者服务器重启了——却从未调用过 `finish`,这次运行就会停留在 `failed`,并带着投影最后捕获到的内容:也就是最后一次轮询时的任务和成员快照。目前还没有 `run resume` 命令;Herdr 不会做任何事情去把一次掉线的运行捡回来。负责人的 `lead_session_id`(在 `kvx workflow run show <run_id> --json` 里)是一个真实的、可恢复的 Claude 会话,所以在一个普通面板里运行 `claude --resume <lead_session_id>` 就能把对话找回来——只是 Herdr 不会替你把这一步接好,而且这样做之后,运行自身的记录仍然停留在 `failed`。

## 运行历史与摘要

```bash
kvx workflow summary show <run_id> [--json]
kvx workflow summary list [<name|id>] [--limit N] [--json]
```

`summary show` 打印结果、摘要正文,以及它所属的运行;`summary list` 在给定某个工作流时按该工作流内最新排在最前,不给目标时则跨所有工作流按最新排在最前。没有摘要的运行——被取消的,或者负责人从未调用过 `finish` 的——是正常的运行,`summary show` 说"没有"也是正常的答案,不是错误。

同一工作流的新运行会自动获得最近若干次前序运行的摘要作为上下文:`workflow.history_context_runs`(默认 3)决定给多少条,写入 `<run dir>/context/prior-runs.md`,并从负责人自己的计划里指向它,让负责人可以从之前运行留下的未竟事项开始。用 `kvx workflow run start --no-prior-summaries` 可以关闭它。

:::caution[`retention_runs` 不会真的清理]
`workflow.retention_runs`(默认 50)仍然是一个公开的配置项,含义仍然是"每个工作流保留这么多次运行,更老的先被清理"——但现在已经没有任何东西会调用真正执行清理的代码了。旧引擎运行结束时的收尾环节曾是清理的唯一调用方,它已随引擎一起消失。这台服务器记录过的每一次运行都会完整保留,直到有人重新接管清理这件事。如果运行历史占用的磁盘空间在今天对你很重要,目前没有任何配置项能帮上忙。
:::

:::caution[恢复与追问已经名存实亡]
运行浏览器里的 `r` 恢复操作,以及 `kvx workflow run start --restore-from <run_id> [--restore <selector>]... [--restore-allow-changed]`,现在仍然能被解析,也仍然会启动一次运行——但恢复一个节点原本意味着从过去某次运行的检查点为它播种,而现在已经没有任何东西会写入节点检查点了(那也曾是旧引擎的工作)。实际上,今天的 `--restore-from` 只是校验请求、把它记录在运行行上,然后启动一次使用相同工作流和相同参数的、普通的全新负责人运行:源运行里实际发生过什么,完全不会传达给新的负责人。同样,`kvx workflow node interrogate`——把过去某个节点的 Claude 会话 fork 进一个面板——现在也总是以 `workflow_node_verb_retired` 作答。**负责人**的会话可以手动恢复(参见上面的"结束一次运行"),但对于单个队友的会话,一旦它的面板消失,就没有对应的手段了。
:::

这次改造之前发布的另外三个 `[workflow]` 配置项——`summary_enabled`、`max_parallel_nodes`、`stuck_threshold`、`drift_threshold`——情况相同:仍然能被解析,仍然有默认值,但不会被任何东西读取。运行的摘要只要负责人调用 `finish` 就会被写入,与 `summary_enabled` 无关;既然现在完全不再调度任何节点,也就没有什么东西会去参考并发数上限或看门狗阈值。这一节里唯一还在起作用的旋钮是 `history_context_runs`。

## 命令

```bash
kvx workflow list [--json]
kvx workflow show <name|id> [--json]
kvx workflow create --file <definition.toml|json> [--name <name>] [--json]
kvx workflow update <name|id> --file <definition.toml|json> [--change-summary <text>] [--json]
kvx workflow run start <name|id> [--tier auto|max|high|medium|low] [--arg KEY=VALUE]... [--no-prior-summaries] [--json]
kvx workflow run list <name|id> [--limit N] [--json]
kvx workflow run show <run_id> [--json]
kvx workflow run cancel <run_id> [--json]
kvx workflow run finish [--run <run_id>] (--summary-file <path> | --summary <text>) [--outcome <word>] [--json]
kvx workflow node show <run_id> <path> [--json]
kvx workflow summary show <run_id> [--json]
kvx workflow summary list [<name|id>] [--limit N] [--json]
```

以上每条命令默认都打印人类可读的文本,加上 `--json` 会得到原始信封结构。在 Herdr 的 TUI 里,`prefix+f` 会打开**工作流启动器**:已保存工作流的列表、所选工作流每个必填参数对应的一行输入框,以及一个由该工作流自身 `default_tier` 初始化的等级行。`Enter` 启动运行;每一行都可以点击。用 `keys.open_workflow_launcher` 可以重新绑定它,DAG 视图对应 `keys.open_workflow_dag`,运行浏览器对应 `keys.open_workflow_runs`。
