**ワークフロー**とは、保存され、バージョン管理された計画です — 名前を持つノード群と、その依存関係、ノードごとのモデル要求から成ります。**実行(run)**は、その計画を対話的な **Claude Code チームリード**1つに Herdr のペイン内で渡し、あとは見守るだけです。リードは計画を読み、Claude Code の共有タスクリストを作成し、チームメイトをそれぞれ独立した Herdr のペインとして起動し、リトライ・再割り当て・完了の判断を自分自身で行います。Herdr は計画を実行しません — 定義し、リードを起動し、チーム自身のタスクリストを観測して実行記録に変換し、結果を保存するだけです。

ワークフローは、計画 → 実装 → レビューのような、一度定義して繰り返し実行したいマルチステップ・マルチエージェントの作業に向いています。すでに動いているエージェント同士の単発的な並行調整には、代わりに[エージェント自動化](/docs/agent-automation/)を使ってください。そして実行は実際の Claude Code エージェントチームであるため、このページと合わせて[Claude Agent Teams](/docs/integrations/#claude-agent-teams)も読んでください — そこに書かれているチームの可否は、Herdr が起動する実行にもそのまま当てはまります。

## ワークフローとは

**ワークフロー**は、1つ以上の **kvdag バージョン**(不変なグラフ定義)を収める名前付きコンテナです。`kvx workflow create` が最初のバージョンを作り、`kvx workflow update` がその上に新しいバージョンを作ります。編集はバージョンをその場で変更することは決してなく、常に新しいバージョンを生みます。そのため過去の実行は、実際に実行されたバージョンに対して常に再現可能です。

実行の開始は、順に5つのことを行います。定義バージョンとその引数を解決し、それらを**リードプロンプト**——リードにどのタスクを、どの順序で、どの `blockedBy` 依存関係付きで作成すべきかを伝えるマークダウンの計画——にレンダリングし、その計画を実行する対話的な `claude` を新しいペインで起動し、リードが作成する Claude Code チームを認識し、そして見守ります。以前は Herdr の仕事だったこと——スケジューリング、クレーム、リトライ、結果をスキーマに照らして判定すること——は、いまはすべてリードの仕事であり、Claude Code 自身の共有タスクリストとリード自身の判断を通じて行われます。実行が終わるのは、リードが `kvx workflow run finish` を呼んで「終わった」と言ったときだけです。

## 定義フォーマット

`kvx workflow create` と `kvx workflow update` は TOML または JSON の定義ドキュメントを読み込みます — ファイル拡張子でフォーマットが決まります。フォーマット自体は変わっていません。変わったのは、実行がそれで何をするかです。今、実際に意味を持つものだけを示す完全な例です:

```toml
name = "ship-feature"
description = "plan → implement → review"
contract = """
Read the codebase before proposing changes. Keep commits small and reviewable.
"""

# Declared run-argument namespace. Without this, `{{goal}}` below has no inbound
# edge port to resolve against and workflow.create rejects the document.
[[arg]]
name = "goal"
required = true
description = "what to build"

[[node]]
key = "plan"
label = "Plan"
demand = "critical"
prompt_template = "Produce an implementation plan for: {{goal}}"

[[node]]
key = "implement"
label = "Implement"
demand = "peak"
prompt_template = "Implement this plan:\n{{plan}}"

[[edge]]
from = "plan"
to = "implement"
```

`contract` は、リードが起動するすべてのチームメイトに繰り返すよう指示される、共通の指示の先頭に付加されます — 横断的なルールはノードごとに繰り返す代わりにここに書いてください。`default_tier`(`auto`、`max`、`high`、`medium`、`low` のいずれか。既定は `high`)は、`kvx workflow run start` に `--tier` が渡されなかったときにこのワークフローの実行が使う階層です。階層がすることは正確に1つだけになりました:各 `demand` ごとにリードへ与えるモデル/エフォートのヒントを絞り込みます(`--tier low` は sonnet を低エフォートで一貫して提案し、`--tier max` は利用可能な最強のモデルを最大エフォートで提案します)——これはヒントであってルールではなく、リードはタスクがそれに値すると判断すればもっと使う自由があります。階層がかつて絞り込んでいた成長上限(`max_nodes`、`max_depth`)は廃止されたエンジンのものです。下の注記を参照してください。

各 `[[arg]]` は、実行引数の名前空間に1つのエントリを宣言し、実行時に `--arg name=value` で埋められます。各 `[[node]]` には一意な `key`、`label`、`prompt_template` が必要です。`role` を指定すると、リードに伝えられるそのノードについての説明が1行増えます。`demand`(`peak`、`critical`、`standard`、`light` のいずれか。既定は `standard`)は、リードがそのノードに使うべきモデルとエフォートへのヒントです——強制するものではなく、タスクがそれに値するとリードが判断すればもっと使う自由があります。各 `[[edge]]` は `from` と `to` だけが必要です:これはリードが作成するタスク計画の中で1つの `blockedBy` 関係になります、それだけです。

`prompt_template` 中の `{{name}}` プレースホルダーは、宣言済みの引数か、入力エッジの `port` 名のいずれかに解決できなければなりません — `workflow.create` は未解決のプレースホルダーを持つドキュメントを依然として拒否し、循環グラフや到達不能なグラフも作成時に依然として拒否されます。宣言済み引数から埋められるプレースホルダーは、リードが目にする前に置換されます。エッジの `port` を指す名前のプレースホルダーは、もう置換され**ません**——Herdr はノードを実行しないため、埋めるべき上流のチェックポイントが存在しないからです。それはレンダリングされた計画の中にそのまま残され、リードには、どのタスク説明にまだ `{{slot}}` マーカーが残っているかが伝えられ、そのチームメイトを起動する際に、ブロックしているタスクの実際の結果からそれを自分で埋めるよう求められます。

拒否された定義は何も書き込みません。`name` はワークフロー間で一意です — 引っかかった場合は `workflow_name_taken` と `kvx workflow update` を参照してください。宣言済みの引数付きで実行します:

```bash
kvx workflow run start ship-feature --arg goal="add dark mode"
```

:::note[互換性のために残っているフィールド]
ノードの `kind`、`runner`、`command`、`max_attempts`、`is_template`、`expand_allow`、`expand_max`、エッジの `kind`、`condition`、`payload`、`port` は、いずれも依然としてパースされ、依然として何もしません——この改修より前に書かれた定義もそのまま読み込めますが、これらは今回のリリースで削除されたカスタム実行エンジンの語彙(スキーマ検証付きノード完了、成長上限で守られたノード拡張、プレーンプロセスとして実行される `runner = "command"` ノード)であり、新しいモデルにはそれに代わるものはありません。ドキュメントレベルの `max_depth`/`max_nodes` もパースされ、階層によって絞り込まれた実行の**実効的な**上限は、いまも計算され実行行に記録されますが、何もそれを強制しません——リードは、必要だと判断すればいくつでもタスクを作成できます。これから作成するドキュメントではこれらを省いてください。ワークフローの計画全体は、いまや `key`、`label`、`role`、`prompt_template`、`demand`、そしてノード間のエッジだけに宿っています。

その古い語彙のうち3つのフィールドは、強制はされないものの、再び何かをするようになりました:`demand` は実行の階層と組み合わさって、リードに与えられるそのノードのモデル/エフォートのヒントを決めます。`output_schema` は、空の既定値より多くを語っているとき、リードのプロンプトにタスクの結果が満たすべき形として描画されます——結果をそれに照らして検証するエンジンはもう存在しないため、あくまで参考情報です。`timeout_ms` はそのタスクの時間予算として描画されます。ウォッチドッグはそれを大幅に超過したこと自体を1つのシグナルとして扱い、通常のナッジを飛ばしてそのタスクを要注意としてマークすることがあります。`isolation` はいまも既定で `none` であり、そこでは何もしませんが、`isolation = "worktree"` は静かに無視される代わりに**作成時に拒否される**ようになりました——実行のペインは worktree に結び付けられないため、それを受け入れると実行が決して果たせない分離を約束してしまうからです。
:::

## 要件と制約

実行は Herdr 専用の仕組みではなく、実際に Herdr の内部で動く実験的な Claude Code の機能です。したがって制約の多くは Claude Code 自身のものです。`kvx workflow run start` は可能な範囲を事前チェックし、うまく動かないリードを黙って起動する代わりに、明確なメッセージで拒否します:

- **エージェントチームは実験的で、バージョンによってゲートされています。** Claude Code 2.1.224 以降が必要です。それより古いバージョンは、エージェントチームなしの通常の `claude` として動きます。Herdr はリードを起動する前に `claude --version` を確認し、その基準を下回れば拒否します(`workflow_lead_unavailable`)。Herdr はリード自身のペインに `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` を設定するため、Herdr が起動する実行のためにこのフラグを自分で設定する必要はありません。
- **分割ペインのチームメイトには Herdr の tmux シムが必要です。** すべての実行は `--teammate-mode tmux` で起動されます。これにより各チームメイトは、リードの端末を共有する見えないインプロセスのセッションではなく、実際の Herdr のペインになります——これはまた、チームメイトが `/resume` を生き延びない理由でもあります。シムの仕組みと何がそれを覆い隠しうるかについては、[Claude Agent Teams](/docs/integrations/#claude-agent-teams)を参照してください。
- **タスクのステータスは遅れることがあります。** アップストリームはこれを明確に文書化しています:チームメイトが、実際には作業を終えているのにタスクを完了とマークし損なうことがあります。そのため Herdr の DAG ビューは2つの信号を並べて表示します——タスク自体のステータスと、所有者ペインの生きたエージェント状態です——まさに、記録が追いつく前に実際には終わっているタスクを見つけられるようにするためです。実行が止まっているように見えたら、タスクリストを信じる前にペインを確認してください。
- **1セッションにつき1チーム、ネストしたチームなし。** 1つのリードセッションはちょうど1つのチームを持ち、チームメイトは自分自身のチームメイトを起動できません。Herdr が1サーバーにつきリードを1つしか動かさないのも同じ理由です——別の実行がすでに動いている間に実行を開始しようとすると、2つ目の管理不能なチームを得る代わりに拒否されます(`workflow_run_in_flight`)。
- **信頼されていないディレクトリは、リードの計画を静かに食い潰します。** Claude Code のフォルダ信頼ダイアログは、信頼されていない `cwd` をただブロックするだけでなく、リードの初期プロンプトを完全に破棄してしまいます。そのためそこで開始された実行は、何もすることがないまま健全に見えて立ち上がります。Herdr は `~/.claude.json` の信頼記録を事前チェックし、正確な対処法とともに拒否します(`workflow_lead_unavailable`):そのディレクトリで一度 `claude` を実行し、ダイアログを承諾してください。
- **セッション間メッセージングには Claude Code 2.1.224 以降と macOS または Linux が必要です。** リードとそのチームメイトは、この機能が利用可能なとき、互いに、またはあなたの他の Claude Code セッションにメッセージを送ることができます——そして Herdr もあなたの代わりに同じことができます:[スタック防止ウォッチドッグ](#スタック防止ウォッチドッグ)と `kvx workflow run message`(DAG ビューの `m`)は、どちらもこの同じチャネルで実行自身のセッションに届き、そのチャネルがなければペインへの直接入力にフォールバックします。ネイティブ Windows では Claude Code のバージョンに関係なく利用できません。また、Claude Code がまだ機能フラグをキャッシュしていないアカウントでのみ効果を持つ環境変数によって、静かに無効化されることがあります。信頼できる生きた信号は、ペインの `/status` に出る `Peer address` 行だけです。
- **実行は設計上、人が付き添う前提です。** 無人モードはありません。権限確認やプラン承認のリクエストはすべて、それを発生させたペイン——たいていはリードのペインです、チームメイトの権限リクエストは既定でリードに上がってくるため——に表示され、実行は人間が答えるまでそこでただ待ちます。これは意図的なものです:v1 全体の操作モデルは「ペインをクリックする」ことです。

## 実行の起動

```bash
kvx workflow run start <name|id> [--tier auto|max|high|medium|low] [--arg KEY=VALUE]... [--json]
```

実行の開始は、アクティブなワークスペース内のフォーカスされたペインを分割し、位置引数のプロンプトなしで対話的な `claude` を起動します——新しい `claude` に argv でプロンプトを渡すと静かに失われてしまう、Herdr が他のエージェントペインですでに知っていたのと同じ失敗モードです。代わりに Herdr は、ペインのセッションが立ち上がるのを待ち、`kvx agent prompt` と同じ仕組みで一度だけ「レンダリングされた計画ファイルを読んで、それに従ってください」という1つの指示を送り込みます。そこから先はリードの仕事です:計画を読み、計画が指定する正確な件名と `blockedBy` 構造を持つタスクを作成し(タスクの件名は `<node-id>: <label>` であり、`node-id:` というプレフィックスが、後で Herdr がタスクをそのノードに一致させる手がかりになります)、自分が担当するノードにちなんだ名前でチームメイトを起動します。

Herdr は、Claude Code のチーム設定が現れた時点でその実行のチームを認識します——リードペインの `cwd` とチームの作成時刻で一致を判定し、一度結び付けたら再導出しません。そのタイミングで実行のステータスは `running` になり、`kvx workflow run show <run_id> --json` は結び付いた `lead_pane_id`、`lead_session_id`、`team_name` を返します。人間向けの既定出力にはこれらは表示されないため、所有者ではなくリード自身のペイン ID が必要なときは `--json` を使ってください。

## 実行を見守る

すべての実行は追跡されるのではなく投影されます:小さなポーラーが2秒ごとに Claude Code 自身の状態を読みます——タスク用の `~/.claude/tasks/<team>/*.json` と、チーム名簿用の `~/.claude/teams/<team>/config.json` です——そしてそれを実行記録に変換します。件名が定義ノードの `<node-id>:` プレフィックスで始まるタスクは、そのノードを更新します。リードが作成したタスクでどのノードにも一致しないものは、破棄されるのではなく、予約されたパス `.task/<n>` の下に**エマージェント**ノードとして記録されます。リードには、計画が求めていなかった作業を分割・統合・追加する自由があるからです。投影されたノードのステータスは、正確に3種類の値のいずれかです——`pending`、`running`(Claude Code の `in_progress`)、`succeeded`(`completed`)——タスクリスト自体の3状態の語彙を映しています。古い、エンジンで実行された実行が持ちうる、より豊かなステータス群(`failed`、`blocked`、`needs_attention`、`skipped`、`restored`)は、この改修より前の実行に属するものであり、新しい実行には決して現れません。チームのメンバーシップは、生きた状態を読むのではなく、観測された変化ごとにスナップショットされます。Claude Code は、リードのセッションが終わった瞬間にチーム設定ディレクトリを削除するからです。

### DAG ビュー

`prefix+shift+F`、またはサイドバーのランチャー(**workflow dag**)から実行の DAG ビューを開きます。ノードのステータスは2層で示されます:投影から得られるタスク自体のステータスと——Herdr の通常のペイン単位のエージェント検出から、タスクの `owner` で結び付けられる——その所有者のペインが `working`、`idle`、`needs input` のいずれであるかです。これがタスクステータスの遅延に対する実践的な答えです:2つが食い違ったら、タスクの記録よりペインを信じてください。ウォッチドッグがあるノードを一度でも見た後は、詳細ストリップにもう1行、`attention:`/`watchdog:` 行が加わります——ウォッチドッグ自身の意見と、実際に消費した段の数です。タスク自身のステータス行を置き換えるのではなく、その隣に並ぶだけです。

| 入力 | 動作 |
| --- | --- |
| `h` / `j` / `k` / `l` または矢印キー | 選択を移動する |
| ノードをクリック | 選択する |
| `Enter`、またはノードをダブルクリック | そのノードのペインにフォーカスする |
| `m` | ペインを開かずに、選択したノードの所有者へのメッセージを作成する(生きた実行のみ) |
| `V` | この実行の[レビューオーバーレイ](#実行をレビューする)を開く |
| `Esc` | DAG ビューを離れる |

フッターは `enter focus pane · m message owner · hjkl move · esc` です。端末の幅に応じて狭まりますが、`esc close` が最後まで残ります。`m` は生きた実行でのみ現れます——過去の実行の Claude Code セッションはすでに終了しており、メッセージを送る相手が残っていないからです。選択したノードを所有しているセッションに宛てられ、誰も担当していないタスクの場合はリードにフォールバックします。`V` はフッターのヒントには含まれません——代わりにヘッダーが独自の控えめな呼びかけを持ちます(下記)——が、このビューのどこにいても機能します。`s` steer も、`i` interrogate も、`Shift+I` reconstruct もありません:それらは Herdr 自身が実行していたノードに対する操作であり、いまやノードは実際のチームメイト自身のペインです。それを操作するには、そのペインを開くことです——次の節で説明します。

実行が終わった後は、ヘッダーにも1行のレビューの呼びかけが表示されます:まだ誰もレビューしていないなら `review available (V)`、面談がまだ進行中なら `reviewing…`、判断待ちの所見があるなら `review ready (V)` です。すでに適用または却下されたサイクルは何も表示しません——この呼びかけはまだ下されていない判断のためのものであり、恒久的なバッジではないからです。`V` を押すと、[実行をレビューする](#実行をレビューする)で説明するオーバーレイが開きます。

### 実行ブラウザ

`prefix+shift+B` は、このサーバーが知っているすべての実行を、すべてのワークフローを横断して新しい順に開きます。`Enter` で実行を DAG ビューで開きます——まだ実行中ならライブで、そうでなければ履歴として読み取り専用で開きます。詳細ストリップには、選択された実行の引数と、あれば要約の結果と最初のハイライトが表示されます。

## スタック防止ウォッチドッグ

もうスケジューリングは何も行われないため、チームメイトを再起動したり、再割り当てしたり、再起動したりする力ももうありません——それらの能力は実行エンジンとともに失われました。Karvex がいまもできるのは、見て、伝えて、記録することです。`workflow.watchdog_tick_secs`(既定 20 秒)ごとに、生きた実行をサンプリングします:チームがまだ `in_progress` と呼んでいる各タスク、そしてリード自身についても、Karvex 自身の画面検出が所有者のペインについて最後に何と言っていたか、そしてそれをどれくらいの時間言い続けているかを読み取ります。作業中のペイン、あるいは前回のサンプル以降に少しでも動いたペインは、すべてリセットされます。タスクが `in_progress` のままなのにペインが動かずにいる状態こそが対処すべきケースです——Claude Code 自身のドキュメントも、チームメイトが作業を終えているのにタスクを完了とマークし損なうことがあると述べています。したがって遅れたステータスだけではそれ自体は証拠になりません。証拠になるのは、ステータスとペインの*食い違い*そのものです。

`workflow.stuck_threshold` 回連続で進捗のないサンプル(既定 3)の後、Karvex は4段のはしごを上ります。1つの配信済みの段から次の段までは `workflow.drift_threshold` サンプル(既定 5)待ちます:**(1)** そのタスク、ステータス、測定されたアイドル時間を名指ししたチームメイトへのナッジ。**(2)** 食い違いそのものを名指しし、タスクを完了とマークするか、ブロックされていると言うか、次に何をするつもりかを言うよう求める構造化された再プロンプト。**(3)** *リード*へのエスカレーション。測定結果と、アップストリーム自身が処方する2つの対処法——再割り当てか、再起動——を添えて。どちらを行えるのもリードだけだからです。**(4)** メッセージを伴わないサーフェシング:ノードの `attention` は `stuck` になり、通知が1つ上がり、`kvx workflow run show --json` がそれを報告します。段3が存在するのはまさに、Karvex 自身にはそのどちらもできない——チームメイトを再起動、再割り当て、再起動することができない——からであり、できるのはリードだけです。アイドルになっている当事者がチームメイトではなくリード自身である場合、はしごはナッジ→再プロンプト→サーフェシングへと短くなります——段3はありません。リードを自分自身にエスカレーションしてもそれは誰にも届かないメッセージになってしまうからです——そして文面もタスクファイルの言葉を使わず、`kvx workflow run finish` を素直に指し示すものになります。実行はそのまま続き、何も強制終了されません。

すべてのメッセージには `[karvex · watchdog]` という枠が付けられ、受け取ったエージェントがランタイムからの操作なのか人間の操作者からなのかを区別できるようにします。そしてどのメッセージも `kvx workflow run message` が使うのと同じ2つのチャネルで送られます:Karvex がそれを持っている場合は受信側セッションの受信箱ソケットへ、持っていない場合はそのペインへの直接入力です。**どちらのチャネルにも届かなかった段は消費されたことになりません**——理由を添えて未配信として記録され、再試行されます。2回失敗して初めて、はしごは話しかけるのをやめてサーフェシングに切り替わります。誰にも届かなかったナッジが、無視されたナッジのように見えてはいけません。これは実際に重要な点です。セッションのメッセージングのエンドポイントは、それを学習した Karvex のプロセスとともに失われるからです。

3つのケースはこのはしごを決して上りません。人間を待っているタスク——ペインが権限確認で止まっている——または完了していない別のタスクを待っているタスクは `attention: needs_input` になります。プロンプトは権限ダイアログに答えられないからです。それ自体が入力を待っているリードは `lead_blocked` になり、その実行のすべてのメンバーが、それぞれ独立にスタックしていると結論づける代わりに、その状態を継承します。ナッジする相手がいないタスク——誰も担当していない、あるいは名簿を離れたチームメイトが担当していた——は段3まで一気に進み、サーフェシングされると `unbound` になります。別に、定義が作成した `timeout_ms` を大幅に超過したタスクは、はしごをまったく上らずに `budget_exceeded` になります。

`attention` はタスクについての Karvex 自身の意見です——決してタスク自身のステータスではありません——固定されず毎サンプルごとに再評価されるため、再び動き出したノードはそれをクリアします。これはノードの `status` とは意図的に別の列です。`status` は Claude Code 自身が投影した事実のままであり、ウォッチドッグは決してステータスを書き込みません。チームが `completed` とマークしたタスクはそもそも監視されません。`kvx workflow node show <run_id> <path>` は、ウォッチドッグに意見があるときは `attention:` 行を、実際に消費した段の数を`interventions:` として(未配信の段を含めて——Karvex は実際に介入したのであり、メッセージが届かなかっただけです)表示します。DAG ビューの詳細ストリップにも同じ2つの事実が表示され、実行が終わった後はヘッダーに控えめなレビューの呼びかけが出ます(下の[実行をレビューする](#実行をレビューする)を参照)。`workflow.watchdog_enabled = false` にすれば全体をオフにできます:分類も、メッセージも、`attention` の書き込みも、サンプリングも一切行われなくなります。

## 実行を操作する

ノードのペインは、完全に独立した Claude Code セッションです——分割ペインモードでは、Claude Code がどこか他の場所で起動するチームメイトとまったく同じものです。もう Herdr 経由の steer、interrupt、restart はありません:

- **1つのチームメイトの方向を変えたいときは**、そのペインを開いて(DAG ビューで `Enter`、または `kvx workflow node show <run_id> <path>` で `pane_id` を見つけます)入力してください。その Claude セッションに直接話しかけていることになります。
- **ペインを切り替えずに短いメッセージを送りたいときは**、DAG ビューで `m` を押すか(あるいはどこからでも `kvx workflow run message --run <run_id> --to <name> --text <text>` を実行します。`<name>` はメンバー名か `team-lead` です)——`m` と同じセッションに、ウォッチドッグ自身が使うのと同じ受信箱ソケットまたはペインへの直接入力のチャネルを通じて、同じ正直な方法で(届いたか、届かなかったか、その理由とともに)記録されて届きます。
- **実行全体の方向を変えたいときは**——優先順位の変更、チームメイトの追加起動、タスクの放棄など——リードのペインを開いて(`kvx workflow run show <run_id> --json` が `lead_pane_id` として名前を返します)望むことを伝えるか、同じ方法でメッセージを送ってください。作業を再割り当てしたり、止まったチームメイトを促したりできるのはリードだけです。Herdr は自分の権限でそのどちらも行えません。
- **リードのペインでの権限確認は、実行全体をブロックします。** チームメイトの権限リクエストは既定でリードに上がるため、止まって見える実行は、その1つのペインでの応答をただ待っているだけであることが非常によくあります。

以前のリリースには `kvx workflow node steer|interrupt|restart|complete|expand|interrogate` がありました。CLI はいまも6つすべてをパースしますが、サーバーはそのすべてに `workflow_node_verb_retired` で応答し、ペインを見るよう案内します——これらは Herdr がもはや実行しないノードに対する操作だったからです。`kvx workflow node show <run_id> <path> [--json]` はいまも動作します:これは投影の読み取りであり、`run show` と同じです。

## 実行を終える

```bash
kvx workflow run finish [--run <run_id>] (--summary-file <path> | --summary <text>) [--outcome <word>] [--json]
```

計画は、すべてのタスクが完了したとき、あるいはこれ以上進められないと結論づけたときに、リードに正確にこれを行うよう指示します:実行の要約をファイルに書き、それを添えて `run finish` を呼ぶことです。`KARVEX_WORKFLOW_RUN_ID` はリード自身のペインにすでにエクスポートされているため、必要なのは要約だけです。この1回の呼び出しが、古いサマライザーの仕組み全体を置き換えます——もうエンジンが判定する結果はありません。実行が本当に失敗した場合でも、リードは `finish` を呼び、そう伝えます:実行自体のステータスはいずれにせよ `succeeded` になります(自己報告が到達できる終端ステータスは他にありません)。実際に何が起きたか、うまくいったかどうかという真実は、`outcome` の単語と要約テキストの中にあり、`kvx workflow summary show` で1コマンド分の距離にあります。

```bash
kvx workflow run cancel <run_id> [--json]
```

キャンセルは実行を `cancelled` にし、リードのペインを閉じます。タスク単位の後始末は必要ありません:チームメイトは Herdr にではなくリードに属しているため、チームを1つずつ回ってペインを閉じるものは何もありません。

リードのペインが `finish` を呼ぶことなくそれ自体で閉じた場合——手動で閉じられた、クラッシュした、サーバーが再起動した、いずれの場合も——実行は投影が最後に捉えていた内容、つまり最後のポーリング時点でのタスクとメンバーのスナップショットとともに `failed` のまま残されます。`run resume` コマンドはまだありません。落ちた実行を拾い上げるために Herdr が行うことは何もありません。リードの `lead_session_id`(`kvx workflow run show <run_id> --json` にあります)は本物の、再開可能な Claude セッションなので、通常のペインで `claude --resume <lead_session_id>` を実行すれば会話は戻ってきます——Herdr がそれを自動で用意してくれるわけではなく、この方法で行っても実行自体の記録は `failed` のままです。

## 実行をレビューする

終了した実行は自分自身をレビューできます:`kvx workflow review start <run_id> [--json]` は Karvex が実際に測定した内容を振り返り、人間の判断を経て、そこから学んだことを新しい定義バージョンに変えます——何がうまくいき、次に何を変えるべきかという Herdr 自身の記録であり、実際に実行されたバージョンに上書きされることは決してありません。レビューは任意で、実行ごとに繰り返し行えます。対象になるのは**終端**の実行(`succeeded`、`failed`、`cancelled`)だけです。まだ進行中の実行に対して開始しようとすると拒否され(`workflow_review_run_not_terminal`)、1つ目のサイクルがまだ `running` か判断待ちのまま2つ目を開始しようとしても拒否されます(`workflow_review_in_flight`)。Karvex がチームを一度も記録しなかった実行にはレビューする相手がおらず、正直にそう答えます(`workflow_review_no_interviewable_members`)。

実行のすべてのメンバー——すべてのチームメイトと、リード自身も予約された `.lead` ノードとして——が候補です。リードが対象に含まれるのは、それが再計画を説明できる唯一の存在だからです。Karvex が測定したこと(タスクの結果、担当者の変更、実際に配信したウォッチドッグの介入)にもとづき、最も問題が多かった順にランク付けされます。実行がきれいに終わらなかった場合はリードが代わりに最初に来ます。悪い実行はリードの実行だからです。`workflow.review_max_interviews`(既定 6)が面談する人数の上限です。上限を超えたメンバーは劣化させられるのではなく、単に完全にスキップされます——そもそも尋ねられません。

対象に残った全員について、Karvex は**フォークされた再開**(`claude --resume <session id> --fork-session`)でその Claude Code セッションを蘇らせます:新しいセッション ID とトランスクリプトが、元のものの複製として、独立したペインの中で始まります。元のセッションとトランスクリプトはまったく手つかずのままです。Karvex は自分が測定した記録——担当していたタスク、それがどう進んだか、実際に受け取ったウォッチドッグのナッジ(そのまま引用して)——をそのフォークに提示し、自分自身の言葉で答えるよう求めます。この方法で決して蘇らせられなかったメンバー(セッション ID が一度も捕捉されなかった、あるいはトランスクリプトがもう読めない)も測定する価値はありますが、その口に言葉を入れる価値はないため、**エビデンスのみ**として面談されます:Karvex は誰も答えないまま、測定したことだけから推論します。

**帰属こそが、このサイクル全体が守ろうとしているルールであり、決して曖昧にされません。** ある所見が再開されたチームメイト自身の証言だと言えるのは、その面談が実際に「再開」として計画され、実際に回答され、Karvex がその2つを結び付ける来歴の記録を持っている場合だけです——それ以外のあらゆる経路は、権限確認で止まった、時間切れになった、回答前にペインを失った面談も含めて、エビデンスのみに劣化します。誰にも、あるいは Karvex が一度も面談していないメンバーに帰属した所見も、同じくエビデンスのみになります。所見を示すすべての場所——`kvx workflow review show`、TUI オーバーレイ、コンパイルされたバージョン自身の `change_summary`——が、この区別をあらゆる所見を1つの見分けのつかないリストに均してしまうことなく、はっきりと示します。エビデンスのみの所見が、あたかもチームメイトが言ったことであるかのように示されることは決してありません。

すべての面談が決着した後——回答されたか、あきらめられたか——、統合ペインがそれらすべてを一緒に見て、定義ノードごとに1つの所見を提案します:**レベル**(`prompt` はそのノードの指示文が誤っていたこと、`structural` は計画自体が誤っていたこと——誤った `demand`、誤った予算、誤ったノードそのもの)、**判定**(`keep` は問題なしとして黙って捨てられるのではなく記録されること、`improve`、あるいは常に完全な置き換えを伴う `replace`)、根拠、そしてそれが拠り所とした証拠です。`kvx workflow review show <run_id> [--json]` は、サイクルの状態と、判断待ちのものについてはその所見を表示します。一度もレビューされたことのない実行は「no review cycle for this run yet」と答えます——これは正常な答えであり、エラーではありません。

判断は `kvx workflow review apply <run_id> (--accept <node_key>... | --decline-all) [--json]` で行い、サイクルが `awaiting_user` のときにのみ到達できます。受け入れなかった所見——`--accept` に含めなかったもの、あるいは `--decline-all` によるサイクル全体——はまったく痕跡を残しません:それについては何も書き込まれません。受け入れられた所見はすべてまとめてコンパイルされるか、まったくコンパイルされないかのどちらかです。手書きの定義が通過するのとまったく同じ作成基準(`isolation = "worktree"` の拒否も含めて)に照らされるため、1つでも不備な所見があれば適用全体が拒否され、原因となった所見が名指しされ、何も書き込まれません——半分だけ適用されたバージョンというものは存在しません。適用に成功すると、`origin: self_improvement` のタグが付き、実行自身のバージョンを親とする新しい**不変の**バージョンが1つ生まれます。実行が実際に実行したバージョンは決して触られません。

`kvx workflow review answer --file <path>` と `kvx workflow review report --file <path>` は、本来は手で入力するものではありません——面談ペインと統合ペイン自身が実行するものであり、どの実行・メンバー・サイクルに属するかを、フラグからではなく自分自身の環境の `KARVEX_WORKFLOW_REVIEW_RUN_ID`/`_MEMBER`/`_CYCLE` から読み取ります。そのため、面談ペインが自分がレビューしている実行以外を指すことは決してありません。

TUI では、DAG ビューで `V` を押すか(あるいは `keys.open_workflow_review`、既定は `prefix+shift+v`、どこからでも)、開いている実行、なければ生きたリードの実行に対するレビューオーバーレイが開きます。サイクルが `awaiting_user` の間:`j`/`k` で選択を移動し、`Space` で選択中の所見の受け入れ状態を切り替え(同じノードキーを共有するすべての所見が一緒に切り替わります。`apply` 自体の粒度に合わせるためです)、`Enter` で切り替えたものすべての適用を提案し、`d`/`D` でサイクル全体の却下を提案します。どちらも一段階の確認を経てからです。`Esc` は何も決めずに閉じます。すべての行が、帰属の一文をはっきりと示します——再開された面談からの、名前入りのチームメイト自身の証言か、あるいはエビデンスのみとその正確な理由かのどちらかを、所見のすぐ隣に。

## 実行履歴と要約

```bash
kvx workflow summary show <run_id> [--json]
kvx workflow summary list [<name|id>] [--limit N] [--json]
```

`summary show` は結果、要約テキスト、そしてそれが属する実行を表示します。`summary list` はあるワークフロー内で新しい順、対象を指定しなければすべてのワークフローを横断して新しい順です。要約のない実行——キャンセルされた、あるいはリードが一度も `finish` を呼ばなかった——は正常な実行であり、`summary show` が「ない」と言うのは正常な答えであってエラーではありません。

同じワークフローの新しい実行には、直近の先行実行の要約が自動的にコンテキストとして提供されます:`workflow.history_context_runs`(既定 3)がその数で、`<run dir>/context/prior-runs.md` に書き込まれ、リード自身の計画からそこが指し示されます。これにより、以前の実行が残した未解決事項からリードが始められます。`kvx workflow run start --no-prior-summaries` で無効化できます。

:::caution[`retention_runs` は削除しません]
`workflow.retention_runs`(既定 50)はいまも公開されている設定キーであり、いまも「ワークフローごとにこれだけの実行数を保持し、古いものから削除する」という意味です——ただし、削除を行うコードを呼ぶものはもうありません。古いエンジンの実行終了時のエピローグが削除の唯一の呼び出し元であり、それはエンジンとともに消えました。このサーバーがこれまでに記録したすべての実行は、削除を再び誰かが担うまで、そのまま丸ごと残り続けます。実行履歴によるディスク使用量が今日気になるなら、それを助けてくれる設定ノブはありません。
:::

:::note[復元は尊重され、尋問は名残りです]
実行ブラウザの `r` 復元アクションと `kvx workflow run start --restore-from <run_id> [--restore <selector>]... [--restore-allow-changed]` は、元の実行のノードチェックポイントを解決し、それを新しいリード自身のプロンプトに、「Restored from a previous run」の下として描画します:どのタスクについて、その要約と保存された結果とともに、何が引き継がれたかです。復元できなかったセレクタ——チェックポイントがない、ペイロードが切り詰められている、あるいは `--restore-allow-changed` なしでプロンプト/スキーマが変わっている——は CLI が表示する復元レポートに報告され、他の通常のタスクと同じように単に新しく計画されます。リードには、どのノードが実際に結果とともに来て、どれが来なかったかが伝えられます。復元が黙って失われたり、推測させられたりすることはありません。`kvx workflow node interrogate`——過去のノードの Claude セッションをペインにフォークすること——はいまも常に `workflow_node_verb_retired` で応答します。**リード**のセッションは手動で再開可能です(上の「実行を終える」を参照)が、1つのチームメイトのセッションについては、そのペインが消えてしまえば同等の手段はありません。
:::

この改修より前に公開されていた他の `[workflow]` キーの1つ、`summary_enabled` はいまも以前のままの話です:パースされ、既定値を持ちますが、いまだ何にも読まれません——実行の要約は、それに関係なくリードが `finish` を呼ぶたびに書き込まれます。`stuck_threshold` と `drift_threshold` はもうそのグループには属しません:[ウォッチドッグ](#スタック防止ウォッチドッグ)が両方を読みます。`max_parallel_nodes` ももうそのグループには属しません——上の並列数のヒントについての段落を参照してください。`history_context_runs` はこの節でもう1つ機能しているノブであり、`review_max_interviews`(既定 6)は今回の改修が新たに加えたものです——[実行をレビューする](#実行をレビューする)を参照してください。

```bash
kvx workflow run start <name|id> [--tier auto|max|high|medium|low] [--arg KEY=VALUE]... [--restore-from <run_id>] [--restore <selector>]... [--restore-allow-changed] [--no-prior-summaries] [--json]
kvx workflow run list <name|id> [--limit N] [--json]
kvx workflow run show <run_id> [--json]
kvx workflow run message [--run <run_id>] --to <name> (--text <text> | --text-file <path>) [--priority now|next|later] [--json]
kvx workflow run cancel <run_id> [--json]
kvx workflow run finish [--run <run_id>] (--summary-file <path> | --summary <text>) [--outcome <word>] [--json]
kvx workflow node show <run_id> <path> [--json]
kvx workflow summary show <run_id> [--json]
kvx workflow summary list [<name|id>] [--limit N] [--json]
kvx workflow review start <run_id> [--json]
kvx workflow review show <run_id> [--json]
kvx workflow review apply <run_id> (--accept <node_key>... | --decline-all) [--json]
kvx workflow review answer --file <path> [--json]
kvx workflow review report --file <path> [--json]
```

上のすべてのコマンドは既定で人間向けのテキストを出力し、`--json` を付けると生のエンベロープになります。`review answer`/`review report` は手で入力するものではなく、面談・統合ペインの中で実行されるものです——[実行をレビューする](#実行をレビューする)を参照してください。Herdr の TUI からは、`prefix+f` で**ワークフローランチャー**を開けます:保存されたワークフローの一覧、選択したワークフローの必須引数ごとの入力行、そのワークフロー自身の `default_tier` から初期化された階層行です。`Enter` で実行を開始します。各行はクリック可能です。`keys.open_workflow_launcher` で割り当てを変更でき、DAG ビューは `keys.open_workflow_dag`、実行ブラウザは `keys.open_workflow_runs`、レビューオーバーレイは `keys.open_workflow_review`(既定 `prefix+shift+v`)で変更できます。
