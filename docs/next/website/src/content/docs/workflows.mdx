A **workflow** is a saved, versioned plan: named nodes, their dependencies, and per-node model demands. A **run** hands that plan to one interactive **Claude Code team lead** in a Herdr pane and steps back. The lead reads the plan, creates Claude Code's shared task list, spawns teammates as their own Herdr panes, and decides retries, reassignment, and completion itself. Herdr does not execute the plan — it defines it, launches the lead, watches the team's own task list and turns it into a run record, and saves what happened.

Workflows are for multi-step, multi-agent work you want to define once and run repeatedly, like plan → implement → review. For one-off parallel coordination between agents you already have running, see [Agent automation](/docs/agent-automation/) instead. And because a run is a real Claude Code agent team, read [Claude Agent Teams](/docs/integrations/#claude-agent-teams) alongside this page — everything a team can and can't do there is true of a Herdr-launched run too.

## What a workflow is

A **workflow** is a named container for one or more **kvdag versions** — immutable graph definitions. `kvx workflow create` makes the first version; `kvx workflow update` authors a new version on top of it. Editing never mutates a version in place; it always produces a new one, so a past run stays reproducible against the version it actually ran.

Starting a run does five things, in order: it resolves the definition version and its args, renders them into a **lead prompt** — a markdown plan telling the lead which tasks to create, in what order, and with which `blockedBy` dependencies — spawns an interactive `claude` in a new pane running that plan, recognizes the Claude Code team the lead creates, and then watches. Everything that used to be Herdr's job — scheduling, claiming, retrying, judging a result against a schema — is the lead's job now, done through Claude Code's own shared task list and its own judgment. A run only finishes when the lead says so, by calling `kvx workflow run finish`.

## Definition format

`kvx workflow create` and `kvx workflow update` read a definition document in TOML or JSON — the file extension selects the format. The format itself hasn't changed; what changed is what a run does with it. This is a complete example of what actually matters now:

```toml
name = "ship-feature"
description = "plan → implement → review"
contract = """
Read the codebase before proposing changes. Keep commits small and reviewable.
"""

# Declared run-argument namespace. Without this, `{{goal}}` below has no inbound
# edge port to resolve against and workflow.create rejects the document.
[[arg]]
name = "goal"
required = true
description = "what to build"

[[node]]
key = "plan"
label = "Plan"
demand = "critical"
prompt_template = "Produce an implementation plan for: {{goal}}"

[[node]]
key = "implement"
label = "Implement"
demand = "peak"
prompt_template = "Implement this plan:\n{{plan}}"

[[edge]]
from = "plan"
to = "implement"
```

`contract` is prepended to the standing instructions the lead is told to repeat to every teammate it spawns — put cross-cutting rules here instead of repeating them per node. `default_tier` (`auto`, `max`, `high`, `medium`, or `low`; default `high`) is the tier runs of this workflow start at when `kvx workflow run start` is given no `--tier`. A tier now does exactly one thing: it narrows the model/effort hints the lead is given per `demand` (`--tier low` suggests sonnet at low effort throughout; `--tier max` suggests the strongest available model at max effort) — hints, not rules, and the lead is free to spend more if a task deserves it. The growth ceilings a tier used to narrow (`max_nodes`, `max_depth`) belong to the retired engine; see the note below.

Each `[[arg]]` declares one entry in the run-argument namespace, filled at run time with `--arg name=value`. Each `[[node]]` needs a unique `key`, a `label`, and a `prompt_template`; `role`, if given, becomes one more line the lead is told about the node. `demand` (`peak`, `critical`, `standard`, or `light`, default `standard`) is a hint towards the model and effort the lead is told to use for that node — nothing enforces it, and the lead can spend more if a task turns out to deserve it. Each `[[edge]]` just needs a `from` and a `to`: it becomes one `blockedBy` relationship in the task plan the lead is told to create, full stop.

`{{name}}` placeholders in a `prompt_template` must resolve to either a declared arg or an inbound edge's `port` name — `workflow.create` still rejects a document with an unresolved placeholder, and a cyclic or unreachable graph is still refused at authoring time. A placeholder filled from a declared arg is substituted before the lead ever sees it. A placeholder naming an edge `port` is **not** substituted any more — Herdr doesn't execute nodes, so there is no upstream checkpoint to fill it with. It is left in the rendered plan exactly as written, and the lead is told which task descriptions still contain a `{{slot}}` marker and asked to fill it from the blocking task's actual result itself, when it spawns that teammate.

A rejected definition writes nothing at all, and `name` is unique across workflows — see `workflow_name_taken` and `kvx workflow update` if you hit it. Run it with the declared args:

```bash
kvx workflow run start ship-feature --arg goal="add dark mode"
```

:::note[Fields kept for compatibility]
`kind`, `runner`, `command`, `max_attempts`, `is_template`, `expand_allow`, `expand_max` on a node, and `kind`, `condition`, `payload`, `port` on an edge, all still parse and still do nothing — a definition written before this rework still loads, but they were the vocabulary of the custom execution engine this release removed (schema-validated node completion, growth-guarded expansion into new nodes, a `runner = "command"` node run as a plain process), and none of them has a replacement in the new model. `max_depth`/`max_nodes` at the document level still parse too, and a run's *effective* ceiling, narrowed by tier, is still computed and recorded on the run row, but nothing enforces it — the lead can create as many tasks as it judges the work needs. Drop all of these from documents you author from here on; a workflow's whole plan now lives in `key`, `label`, `role`, `prompt_template`, `demand`, and the edges between nodes.

Three fields from that old vocabulary do something again, read rather than enforced: `demand`, paired with the run's tier, decides the model/effort hint the lead is given for a node. `output_schema`, when it says more than the empty default, is rendered into the lead's prompt as the shape a task's result should match — informational, since there is no engine left to validate a result against it. `timeout_ms` is rendered as that task's time budget; the watchdog treats badly overrunning it as a signal on its own and can mark the task as needing attention, skipping its usual nudge. `isolation` still defaults to `none` and does nothing there, but `isolation = "worktree"` is now **rejected at authoring time** rather than silently ignored — no run pane is bound to a worktree, so accepting it would promise isolation a run can never deliver.
:::

## Requirements and constraints

A run is a real, experimental Claude Code feature running inside Herdr, not a Herdr-only mechanism, so its constraints are largely Claude Code's own. `kvx workflow run start` preflights what it can and refuses with a clear message rather than launching a lead that quietly can't do its job:

- **Agent teams are experimental and version-gated.** They need Claude Code 2.1.224 or newer; older ships as normal, agent-team-less `claude`. Herdr checks `claude --version` before spawning a lead and refuses (`workflow_lead_unavailable`) below that floor. Herdr also sets `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in the lead's own pane, so you don't need to set the flag yourself for a Herdr-launched run.
- **Split-pane teammates need Herdr's tmux shim.** Every run is launched with `--teammate-mode tmux`, which is what makes each teammate a real Herdr pane instead of an invisible in-process session sharing the lead's terminal — this is also why teammates never survive `/resume`. See [Claude Agent Teams](/docs/integrations/#claude-agent-teams) for how the shim works and what can shadow it.
- **Task status can lag.** Upstream documents this plainly: a teammate sometimes doesn't mark its task complete even though the work is done. Herdr's DAG view therefore shows two signals side by side — the task's own status and the owning pane's live agent state — precisely so you can catch a task that finished in reality before its record catches up. If a run looks stuck, check the pane before you believe the task list.
- **One team per session, no nested teams.** A lead session has exactly one team; a teammate cannot spawn its own teammates. Herdr runs exactly one lead per server for the same reason — starting a run while another is live is refused (`workflow_run_in_flight`) rather than getting a second, unmanageable team.
- **Untrusted directories silently eat the lead's plan.** Claude Code's folder-trust dialog doesn't just block an untrusted `cwd` — it discards the lead's initial prompt entirely, so a run started there comes up looking healthy with nothing to do. Herdr preflights `~/.claude.json`'s trust record and refuses (`workflow_lead_unavailable`) with the exact remedy: run `claude` in that directory once and accept the dialog.
- **Cross-session messaging needs Claude Code 2.1.224+ and macOS or Linux.** Herdr doesn't send messages on your behalf — steering is clicking a pane and typing — but the lead and its teammates can message each other and your other Claude Code sessions using this feature, when it's available. It is unavailable on native Windows regardless of Claude Code version, and can be silently disabled by environment variables that only take effect on an account Claude Code hasn't already cached feature flags for; the `Peer address` row in a pane's `/status` is the one live signal worth trusting.
- **Runs are attended by design.** There is no unattended mode. Permission prompts and plan-approval requests all surface in the pane that raised them — usually the lead's, since teammate permission requests bubble up to the lead — and a run just sits there until a human answers. This is deliberate: v1's whole interaction model is "click on the pane."

## Launching a run

```bash
kvx workflow run start <name|id> [--tier auto|max|high|medium|low] [--arg KEY=VALUE]... [--json]
```

Starting a run spawns a split of the focused pane in the active workspace, running an interactive `claude` with no positional prompt — a prompt handed to a fresh `claude` on argv is silently lost, the same failure mode Herdr already knew for other agent panes. Instead, Herdr waits for the pane's session to come up and then seeds it once, through the same mechanism as `kvx agent prompt`, with one instruction: read the rendered plan file and follow it. From there the lead is on its own: it reads the plan, creates tasks with the exact subjects and `blockedBy` structure the plan names (a task subject is `<node-id>: <label>`, and the `node-id:` prefix is what lets Herdr match a task back to its node later), and spawns teammates named after the nodes they own.

Herdr recognizes the run's team once Claude Code's team config appears — matched by the lead pane's `cwd` and the team's creation time, bound once and never re-derived. The run's status becomes `running` at that point, and `kvx workflow run show <run_id> --json` reports `lead_pane_id`, `lead_session_id`, and `team_name` once bound; the human-readable default output doesn't print them, so reach for `--json` when you need the lead's own pane id rather than its owner's.

## Watching a run

Every run is projected, not tracked: a small poller reads Claude Code's own state every two seconds — `~/.claude/tasks/<team>/*.json` for tasks and `~/.claude/teams/<team>/config.json` for the team roster — and turns it into run records. A task whose subject starts with a definition node's `<node-id>:` prefix updates that node; a task the lead created that matches no node is recorded as an **emergent** node under the reserved path `.task/<n>` rather than dropped, because the lead is allowed to split, merge, or add work the plan didn't ask for. A projected node's status is one of exactly three values — `pending`, `running` (Claude Code's `in_progress`), `succeeded` (`completed`) — mirroring the task list's own three-state vocabulary; the richer statuses an older, engine-executed run can carry (`failed`, `blocked`, `needs_attention`, `skipped`, `restored`) belong to runs from before this rework and never appear on a new one. Team membership is snapshotted on every observed change rather than read live, because Claude Code deletes the team config directory the moment the lead's session ends.

### The DAG view

Open a run's DAG view with `prefix+shift+F`, or from the sidebar launcher (**workflow dag**). Node status is shown two layers deep: the task's own status from the projection, and — from Herdr's ordinary per-pane agent detection, joined by the task's `owner` — whether that owner's pane is `working`, `idle`, or `needs input`. This is the practical answer to task status lag: trust the pane over the task record when the two disagree.

| Input | Action |
| --- | --- |
| `h` / `j` / `k` / `l` or the arrow keys | move the selection |
| Click a node | select it |
| `Enter`, or double-click a node | focus that node's pane |
| `Esc` | leave the DAG view |

That's the whole footer now — `enter focus pane · hjkl move · esc`. There is no `s` steer, no `i` interrogate, no `Shift+I` reconstruct: those operated on a node Herdr executed itself, and a node is a real teammate's own pane now. Steering it is opening that pane, below.

### The run browser

`prefix+shift+B` opens every run this server knows about, newest first, across every workflow. `Enter` opens a run in the DAG view — live if it is still running, read-only from history otherwise. The detail strip shows the selected run's args and, once it has one, its summary's outcome and first highlight.

## Steering a run

A node's pane is a full, independent Claude Code session — in split-pane mode, exactly the same as any teammate Claude Code spawns anywhere else. There is no Herdr-mediated steer, interrupt, or restart any more:

- **To redirect one teammate**, open its pane (`Enter` in the DAG view, or find its `pane_id` on `kvx workflow node show <run_id> <path>`) and type. You're talking to that Claude session directly.
- **To redirect the run as a whole** — reprioritize, spawn more teammates, abandon a task — open the lead's pane (`kvx workflow run show <run_id> --json` names it as `lead_pane_id`) and tell it what you want. The lead is the one thing that can reassign work or nudge a stalled teammate; Herdr can't do either on its own behalf.
- **A permission prompt in the lead's pane blocks the entire run.** Teammate permission requests bubble up to the lead by default, so a run that looks stuck is very often just waiting on an answer in that one pane.

Earlier releases had `kvx workflow node steer|interrupt|restart|complete|expand|interrogate`. The CLI still parses all six for now, but the server answers every one of them with `workflow_node_verb_retired` and points you at the pane — they executed a node Herdr no longer executes. `kvx workflow node show <run_id> <path> [--json]` still works; it's a read of the projection, same as `run show`.

## Finishing a run

```bash
kvx workflow run finish [--run <run_id>] (--summary-file <path> | --summary <text>) [--outcome <word>] [--json]
```

The plan tells the lead to do exactly this once every task is done, or once it has concluded the run can't go further: write a run summary to a file, then call `run finish` with it. `KARVEX_WORKFLOW_RUN_ID` is already exported in the lead's own pane, so it needs nothing but the summary. This one call replaces the entire old summariser subsystem — there is no engine-judged verdict any more. If the run genuinely failed, the lead still calls `finish` and says so: the run's own status becomes `succeeded` regardless (there's no other terminal status a self-report can reach), and the truth — what actually happened, and whether it worked — lives in the `outcome` word and the summary text, one `kvx workflow summary show` away.

```bash
kvx workflow run cancel <run_id> [--json]
```

Cancelling marks the run `cancelled` and closes the lead's pane. There's no task-level teardown to do: teammates belong to the lead, not to Herdr, so nothing walks the team closing panes one by one.

If the lead's pane closes on its own — closed by hand, crashed, or the server restarted — without ever calling `finish`, the run is left `failed` with whatever the projection last captured: the task and member snapshots as of the last poll. There is no `run resume` command yet; there is nothing Herdr does to pick a dropped run back up. The lead's `lead_session_id` (on `kvx workflow run show <run_id> --json`) is a real, resumable Claude session, so `claude --resume <lead_session_id>` in a plain pane gets the conversation back — Herdr just doesn't wire that up for you, and doing it this way leaves the run's own record `failed`.

## Run history and summaries

```bash
kvx workflow summary show <run_id> [--json]
kvx workflow summary list [<name|id>] [--limit N] [--json]
```

`summary show` prints the outcome, the summary text, and the run it belongs to; `summary list` is newest-first across a workflow, or across every workflow when given no target. A run with no summary — cancelled, or the lead never called `finish` — is a normal run, and `summary show` saying there is none is a normal answer, not an error.

A new run of the same workflow is offered its most recent predecessors' summaries as context automatically: `workflow.history_context_runs` (default 3) is how many, written to `<run dir>/context/prior-runs.md` and pointed at from the lead's own plan, so it can start from what previous runs left open. Opt out with `kvx workflow run start --no-prior-summaries`.

:::caution[`retention_runs` doesn't prune]
`workflow.retention_runs` (default 50) is still a published config key, and it still means "keep this many runs per workflow, oldest pruned first" — but nothing calls the code that prunes any more. The old engine's end-of-run epilogue was retention's only caller, and it went with the engine. Every run this server has ever recorded stays, in full, until something is given ownership of pruning again. If disk use from run history matters to you today, there's no config knob that helps.
:::

:::note[Restore is honoured, interrogate is vestigial]
The run browser's `r` restore action and `kvx workflow run start --restore-from <run_id> [--restore <selector>]... [--restore-allow-changed]` resolve the source run's node checkpoints and render them into the new lead's own prompt, under "Restored from a previous run": what got carried forward, per task, with its summary and its stored result. A selector that couldn't be restored — no checkpoint, a truncated payload, or a changed prompt/schema without `--restore-allow-changed` — is reported in the restore report the CLI prints, and is simply planned fresh like any other task; the lead is told which nodes actually came with a result and which did not, rather than either silently missing the restore or having to guess. `kvx workflow node interrogate` — forking a past node's Claude session into a pane — still always answers `workflow_node_verb_retired`; a *lead's* session is resumable by hand (see Finishing a run, above), but there is no equivalent for a single teammate's session once its pane is gone.
:::

Two of the other `[workflow]` keys published before this rework, `summary_enabled` and `stuck_threshold`/`drift_threshold`, are still the earlier story: parsed, defaulted, and read by nothing yet. A run's summary is written whenever the lead calls `finish`, regardless of `summary_enabled`; nothing ticks a watchdog on this release, so nothing consults a stuck or drift threshold either. `max_parallel_nodes` is no longer one of them — see the concurrency-hint paragraph above. `history_context_runs` is the other working knob in the section.

## Commands

```bash
kvx workflow list [--json]
kvx workflow show <name|id> [--json]
kvx workflow create --file <definition.toml|json> [--name <name>] [--json]
kvx workflow update <name|id> --file <definition.toml|json> [--change-summary <text>] [--json]
kvx workflow run start <name|id> [--tier auto|max|high|medium|low] [--arg KEY=VALUE]... [--no-prior-summaries] [--json]
kvx workflow run list <name|id> [--limit N] [--json]
kvx workflow run show <run_id> [--json]
kvx workflow run cancel <run_id> [--json]
kvx workflow run finish [--run <run_id>] (--summary-file <path> | --summary <text>) [--outcome <word>] [--json]
kvx workflow node show <run_id> <path> [--json]
kvx workflow summary show <run_id> [--json]
kvx workflow summary list [<name|id>] [--limit N] [--json]
```

Every command above prints human-readable text by default and takes `--json` for the raw envelope. From the Herdr TUI, `prefix+f` opens the **workflow launcher**: saved workflows, one input line per required argument, a tier row seeded from the workflow's `default_tier`. `Enter` starts the run; every row is clickable. Rebind it with `keys.open_workflow_launcher`, the DAG view with `keys.open_workflow_dag`, and the run browser with `keys.open_workflow_runs`.
